Architecture at a Glance

The engine is organized around three orthogonal concerns: identity & ownership (the Object → Node tree), spatial representation (the Shape2D hierarchy used for both drawing and collision), and global services (three singletons: RenderServer, PhysicsServer, GravityServer). Every node that should appear on screen inherits from CanvasItem, which auto-registers itself with the RenderServer on construction. Every collision-capable node inherits from CollisionObject2D, which auto-registers with the PhysicsServer. Every gravity-affected body inherits from PhysicsBody2D, which auto-registers with the GravityServer. This means construction is registration: new Particle(...) is enough to make a body visible, collidable, and gravitationally active.

Class hierarchy. Green outlines indicate singleton servers; the orange GravityServer uses the Fast Multipole Method. Dashed "→ regs w/" labels show the auto-registration side effects performed by each constructor.

Quick Start

The smallest possible application boots the three servers, spawns one particle, and runs the main loop. Note how new Particle(...) alone is sufficient to make the body visible, collidable, and gravitationally active — all three servers learn about it automatically through constructor side-effects.

C++ 
#include "../classes/gravity_server/GravityServer.hpp"
#include "../classes/node/canvas_item/node2d/collision_object2d/physics_body2d/particle/Particle.hpp"
#include "../classes/physics_server/PhysicsServer.hpp"
#include "../classes/render_server/RenderServer.hpp"
#include "../include/raylib-cpp.hpp"

int main(void) {
    // 1. Boot all three singletons
    GravityServer::getInstance();
    PhysicsServer::getInstance();
    RenderServer::getInstance();

    // 2. Spawn a particle — auto-regs with all 3 servers
    Particle* p = new Particle("P0",
        raylib::Vector2(400, 300),
        raylib::Color::White());
    p->setMass(2.0f);

    // 3. Window + main loop
    raylib::Window window(800, 600);
    while (!window.ShouldClose()) {
        window.BeginDrawing();
        window.ClearBackground();

        PhysicsServer::getInstance().rebuild();
        GravityServer::getInstance().rebuild();
        GravityServer::getInstance().applyGravity();
        p->updatePhysics();

        RenderServer::getInstance().render(window);
        window.EndDrawing();
    }
    delete p;
    return 0;
}

Core Concepts

Before diving into individual classes, four foundational patterns are worth understanding because every other class in the engine is built on top of them. These patterns explain why the API looks the way it does, and once you internalize them, the rest of the engine reads almost mechanically.

1. Object Identity

Every entity in the engine — every node, every shape, every server — inherits from Object. The Object base class hands out a monotonically-increasing unsigned long _instanceID at construction time. This ID is the only stable handle you can hold across copies, moves, and pointer reassignments: the copy constructor assigns a fresh ID rather than duplicating the source's, so two objects that compare unequal via operator== are guaranteed to have different IDs even if every other field is identical.

This matters because the three singleton servers all key their internal maps on _instanceID. When you call PhysicsServer::removeCollisionObject(this) from the CollisionObject2D destructor, the lookup is an O(1) hash on the ID — no pointer comparisons, no name lookups, no ambiguity. The ID is also what makes the GravityServer's acceleration map work: during applyGravity() the FMM accumulates per-body accelerations in an unordered_map<unsigned long, Vector2>, then a second pass dispatches applyForce() back to each body by ID.

2. Node Tree & Ownership

The Node class extends Object with a parent pointer and a vector of child pointers. This is a classic Godot-style scene graph: a parent owns its children, the destructor recursively deletes every child, and child positions/rotations inherit (and propagate deltas to) their parent's transform. When you write particle.pushBackChild(sprite), you are transferring ownership of sprite's lifetime to the particle — destroying the particle will destroy the sprite automatically.

The tree is intentionally not reference-counted. This keeps the hot path (the per-frame update loop over 2000+ particles) free of atomic refcount operations, at the cost of requiring the user to pick exactly one owner for each node. The setParent method auto-removes the node from its previous parent, so reparenting is safe but the previous parent must still be alive.

3. Constructor Side-Effects (Auto-Registration)

This is the single most important pattern in the engine. The constructor of CanvasItem calls RenderServer::addCanvasItem(this). The constructor of CollisionObject2D calls PhysicsServer::addCollisionObject(this). The constructor of PhysicsBody2D calls GravityServer::addBody(this). The destructors all call the matching remove. The practical consequence is that creating a node is sufficient to make it part of the engine's update loops — there is no separate "register" or "spawn" call to forget.

Tip. Because registration happens in the base-class constructor, you never need to call addBody / addCollisionObject / addCanvasItem yourself for any subclass. The only time you'd call them directly is if you were writing a brand-new base class outside the existing hierarchy.

4. Singleton Servers

RenderServer, PhysicsServer, and GravityServer all follow the same pattern: a private default constructor, a static _instance pointer, a public getInstance() that lazily allocates on first call, and a deleteInstance() for shutdown. The bodies/canvas-items/collision-objects they track are stored in static maps keyed by instance ID, which means the maps survive even if you momentarily delete the singleton instance — but since the maps are only ever read from inside getInstance()-returned references, this is mostly an implementation detail.

The singleton pattern is a deliberate tradeoff: it removes the need to thread a "world" or "scene" object through every function call, at the cost of making the engine fundamentally single-scene. For the particle-simulator use case this engine was built for, that tradeoff is a clear win.

5. Fluent Setter API

Almost every setter in the engine returns *this by reference, so calls chain naturally:

C++ 
particle.setMass(2.0f)
       .setLockRotation(true)
       .setLinearVel(raylib::Vector2(10, 0));

This is borrowed from Godot's convention and works particularly well when configuring a node immediately after construction, as seen in main.cpp's spawnParticles helper.

Foundation: Object & Vector2i

These two types are the bedrock of the engine. Object is the universal base class — everything inherits from it, directly or indirectly. Vector2i is a tiny integer vector used as a hash key by PhysicsServer's spatial grid.

Object

: (root base class) classes/Object.hpp
Object exists to give every entity in the engine a stable, unique identity (the _instanceID) and a uniform introspection surface (getClassName(), getInstanceName(), operator<<). The ID is what the three singleton servers use as a hash key — without it, the engine would need pointer-keyed maps (which break when objects move in memory) or string-keyed maps (which are slow and ambiguous). Because the copy constructor allocates a new ID, two objects are never accidentally aliased.

Public API

public explicit Object(const std::string &instanceName = "")
Default constructor. Assigns a fresh _instanceID by post-incrementing the static counter, stores the optional human-readable name.
public explicit Object(const Object &other)
Copy constructor. Gets a new ID (does not copy other._instanceID) but copies the name. This guarantees two distinct objects always have distinct IDs.
public unsigned long getInstanceID() const noexcept
Returns the unique identifier. Stable for the lifetime of the object. Used as the hash key in all three server maps.
public const std::string & getInstanceName() const noexcept
Returns the human-readable name. Non-unique; multiple objects can share a name. Used by Node::findChild(name).
public Object & setInstanceName(const std::string &instanceName = "") noexcept
Mutator (fluent). Returns *this so it can chain with other setters.
public virtual const std::string & getClassName() const noexcept
Virtual — overridden by every subclass to return a static string like "Particle" or "GravityServer". Used by Node::findClass() and by the collision dispatcher in PhysicsBody2D::collideWith to identify shape types via string comparison.
public bool operator==(const Object &other) const noexcept
Identity comparison — true iff _instanceID matches. Two objects with the same name but different IDs compare unequal.

Example

C++ 
Object a("hero"), b("hero");
// a and b have the same name but different IDs
assert(a != b);                       // true: IDs differ
assert(a.getInstanceName() == b.getInstanceName()); // true: same name
std::cout << a;  // prints "Object#0: \"hero\""

Vector2i

: struct (no base) classes/Vector2i.hpp
Vector2i is a 2D integer vector used as a hash key by PhysicsServer's spatial grid. Raylib's Vector2 is float-based and has no std::hash specialization, so it cannot be used as an unordered_map key directly. Rather than specializing std::hash for raylib::Vector2 (which would be invasive), the engine introduces a tiny standalone integer vector with a companion Vector2iHash functor that uses the classic Boost-style 0x9e3779b9 mix.

Public API

public constexpr Vector2i(int x = 0, int y = 0) noexcept
Default/component constructor. constexpr so it can be used in compile-time contexts.
public constexpr Vector2i(const raylib::Vector2 &v) noexcept
Implicit conversion from raylib::Vector2. Truncates (does not round). Used by PhysicsServer::hashFunction which divides a float position by CELL_SIZE and relies on the implicit conversion.
public constexpr bool operator==(const Vector2i &other) const noexcept
Required for unordered_map key equality.

Vector2iHash

The companion hash functor. Implements the Boost hash-combine idiom: h ^= v.y + 0x9e3779b9 + (h << 6) + (h >> 2). The constant 0x9e3779b9 is 2^32 / φ (golden ratio), which distributes bits well. Used as the third template argument to std::unordered_map<Vector2i, ..., Vector2iHash>.

C++ 
// How PhysicsServer uses it:
std::unordered_map<Vector2i, std::vector<CollisionObject2D*>, Vector2iHash> _hashMap;

Vector2i hashFunction(const raylib::Vector2& p) const noexcept {
    return p / 10.0f;  // implicit Vector2 -> Vector2i via constructor
}

Node Hierarchy: Node → CanvasItem → Node2D

These three classes form the spine of the scene graph. Node adds the parent/child tree, CanvasItem adds visibility and auto-registration with RenderServer, and Node2D adds a 2D transform (position + rotation) that propagates deltas to its children.

Node

: public Object classes/node/Node.hpp
Node is the engine's scene-graph primitive. It owns its children via raw pointers and deletes them in its destructor — this avoids refcounting overhead in the hot loop and matches Godot's ownership model. The class also provides virtual ready(), update(), updatePhysics() hooks that subclasses override to plug into the frame loop.

pushFrontChild(Node&)Prepend child.Useful for draw-order overrides.

Example: build a small subtree

C++ 
Node root("root");
Node* child1 = new Node("c1");
Node* child2 = new Node("c2");
root.pushBackChild(*child1);
root.pushBackChild(*child2);

// Find by name
auto matches = root.findChild("c1");  // [child1]

// Deleting a child frees memory and removes from parent
root.deleteChild("c1");  // child1 is now deleted

// root's destructor will delete child2 automatically

CanvasItem

: public Node classes/node/canvas_item/CanvasItem.hpp
CanvasItem is the bridge between the scene graph and the render pipeline. Its constructor calls RenderServer::addCanvasItem(this) and its destructor calls removeCanvasItem, so any CanvasItem subclass is automatically drawn every frame by the RenderServer. It also owns the visibility flags (_visible, _visibleDebug) and the render layer, plus the isInView() culling tests that RenderServer uses to skip off-screen items.

Public API

public bool isVisible() const noexcept
Whether draw() will be called by RenderServer. Default true.
public CanvasItem & setVisible(bool) noexcept
Toggle visibility. Items with _visible=false are skipped entirely by the render loop.
public bool isVisibleDebug() const noexcept
Whether drawDebug() will also be called. Default false. Useful for visualizing collision shapes, velocities, etc.
public CanvasItem & setVisibleDebug(bool) noexcept
Enable debug overlay drawing. Node2D::drawDebug draws a small red+green axis gizmo and a blue origin dot.
public int getLayer() / setLayer(int) noexcept
Render layer (reserved for future z-ordering; currently not used by RenderServer).
public bool isInView(const Window&, const Vector2& pos) const noexcept
Returns true if pos is inside the window's screen-space rectangle. Used by RenderServer for culling.
public bool isInView(const Window&, const Camera2D&, const Vector2& pos) const noexcept
Camera-aware variant. Computes the visible world rectangle from the camera's target & zoom, then tests pos against it.
public bool isInView(const Window&, const Shape2D&, const Vector2& shapePos) const noexcept
Shape-aware variant. Builds a screen-sized RectangleShape2D and tests collision with the given shape — useful for large sprites that may straddle the screen edge.
virtual void draw() const noexcept = 0
Pure virtual — every subclass implements its own rendering. Node2D's impl is empty (invisible); Sprite2D draws texture or shape; Button draws a rounded rectangle with text.
virtual void drawDebug() const noexcept = 0
Pure virtual debug overlay. Called only if _visibleDebug is true.

Node2D

: public CanvasItem classes/node/canvas_item/node2d/Node2D.hpp
Node2D adds a 2D transform (_pos, _rot) and the delta-propagation rule: when you call setPos(newPos), the node computes deltaPos = newPos - _pos and then recursively calls setPos(child.getPos() + deltaPos) on every Node2D child. The same is true for setRotation. This means moving a parent moves the entire subtree rigidly, which is exactly the behavior you want for a Particle that owns its Sprite2D and CollisionShape2D children.

Public API

public const Vector2 & getPos() const noexcept
Const accessor for _pos. Returns by reference — no copy.
public Vector2 & getPos() noexcept
Non-const accessor. Warning: bypasses delta-propagation. Use setPos() if you have children that should follow.
public Node2D & setPos(const Vector2 &newPos) noexcept
Set position and propagate the delta to all Node2D children. dynamic_casts each child — non-Node2D children are skipped.
public float getRotation() const noexcept
Rotation in radians (despite the field name, no implicit unit conversion is done — callers must convert from degrees if needed).
public Node2D & setRotation(float newRot) noexcept
Set rotation (radians) and propagate delta to Node2D children.
virtual void drawDebug() const noexcept override
Draws a tiny axis gizmo: 10-pixel red line for +X, 10-pixel green line for +Y, and a small blue circle at the origin. The lines are rotated by _rot so you can visually confirm the orientation.

Delta-propagation example

C++ 
Node2D parent("parent");
Node2D* child = new Node2D("child");
child->setPos(Vector2(5, 0));   // child at (5,0), parent at (0,0)
parent.pushBackChild(*child);

parent.setPos(Vector2(100, 100));
// parent is now at (100,100), child is at (105,100) — moved by delta

Visual & UI Nodes: Sprite2D, Control, Button

This group covers everything you actually see on screen. Sprite2D renders a texture or procedural shape; Control is the base class for UI widgets (currently a thin marker class awaiting future UI primitives); Button is a fully-functional clickable button with hover/press state, rounded borders, and an onClick callback.

Sprite2D

: public Node2D classes/node/canvas_item/node2d/sprite2d/Sprite2D.hpp
Sprite2D is the universal visual primitive. It can render either a GPU texture (_texture) or a procedural Shape2D (circle/rectangle) — if the texture's id != 0, the texture wins; otherwise the shape is drawn. This dual-mode design lets you use the same class for both image-based sprites and procedural particles, which is why Particle uses a Sprite2D child with a CircleShape2D rather than needing its own draw code.

Public API

public Sprite2D & setShape(float width, float height) noexcept
Set a rectangle shape. If a RectangleShape2D already exists, mutates its size; otherwise allocates a new one. If a circle is currently set, replaces it.
public Sprite2D & setShape(float radius) noexcept
Set a circle shape. Same replace-if-different-type logic as the rectangle variant.
public Sprite2D & setColor(const Color &) noexcept
Tint color for both texture and shape rendering.
public Sprite2D & setTexture(Texture2D &&) noexcept
Move-assign a texture. The texture's id != 0 check in draw() is what flips rendering into texture mode.
public Sprite2D & setOffset(const Vector2 &) / setScale(float) / setRotation(float) noexcept
Local transform relative to the parent Node2D. The sprite's effective rotation is _rot + _rotation (parent + local).
virtual void draw() const noexcept override
Renders either texture (via Texture2D::Draw) or shape (circle via DrawCircle, rectangle via Rectangle::Draw with a center offset for proper rotation pivot). Combines parent rotation + local rotation, applies scale, applies tint color.

Texture vs Shape dispatch

C++ 
void Sprite2D::draw() const noexcept {
    if (_texture.id != 0) {
        _texture.Draw(_pos + _offset, (_rot + _rotation) * RAD2DEG, _scale, _color);
    } else if (_shape != nullptr) {
        // ...circle or rectangle branch on _shape->getClassName()
    }
}

Control

: public CanvasItem classes/node/canvas_item/control/Control.hpp
Control is the UI counterpart to Node2D: just as Node2D adds a 2D transform to CanvasItem for world-space entities, Control is intended as the base class for screen-space UI widgets. In the current codebase it's a thin marker class — the hierarchy slot is reserved so that future UI primitives (Label, LineEdit, Slider, etc.) have a natural place to live and can share anchor/margin logic. Button already inherits from it.
public Control(const std::string &instanceName = "")
Constructor — just forwards to CanvasItem. No additional state yet.

Button

: public Control classes/node/canvas_item/control/button/Button.hpp
Button is a self-contained, immediate-mode-style clickable widget. Unlike the rest of the engine (which is retained-mode via the scene graph), the button polls raylib's mouse state inside update() and fires its onClick callback the moment a click is detected. This makes it trivial to use — no event bus, no signal system, just setOnClick([]{...}).

Constructors (5 overloads for convenience)

ConstructorUse case
Button(x, y, w, h, text)Scalar components — most common.
Button(x, y, Vector2 size, text)Size as a vector.
Button(Vector2 pos, w, h, text)Position as a vector.
Button(Vector2 pos, Vector2 size, text)Both as vectors.
Button(Rectangle bounds, text)From an existing rectangle.

State machine

The button tracks three boolean flags: isHovered (mouse inside bounds), isPressed (mouse inside bounds AND left button down), and wasPressed (previous-frame isPressed). A click is detected as the rising edge: wasPressed && !isPressed && isHovered. The color picker selects among normalColor, hoverColor, pressedColor based on the current state.

Public API

virtual void update() noexcept override
Polls mouse, updates isHovered / isPressed, fires onClick on rising-edge release. Must be called every frame for the button to work.
virtual void draw() const noexcept override
Renders background (rounded or rectangular), optional border, centered text label, and a 40%-alpha black overlay if disabled.
public Button & setOnClick(std::function<void()>)
Register the click callback. Uses std::function so lambdas with captures work.
public Button & setColors(normal, hover, pressed)
Triple-color setter for the three states. Defaults are (100,100,100), (130,130,130), (70,70,70).
public Button & setRoundness(float r) / setBorderWidth(float) / setBorderColor(Color)
Visual customization. roundness is clamped to [0,1]. Border is only drawn if borderWidth > 0.
public Button & setEnabled(bool) / bool isEnabled()
Disabled buttons don't poll mouse, render with a dark overlay, and never fire onClick.

Full fluent-API example

C++ 
Button btn(50, 50, 200, 50, "Spawn Particle");
btn.setColors(Color(60,120,200),
              Color(80,150,230),
              Color(40,90,160))
   .setRoundness(0.3f)
   .setBorderWidth(2.0f)
   .setBorderColor(Color::White())
   .setOnClick([&](){
       particles.push_back(new Particle("P", randomPos(), Color::Red()));
   });

// In main loop:
btn.update();   // polls mouse + may fire onClick
btn.draw();    // renders the button

Collision System: CollisionShape2D → CollisionObject2D → PhysicsBody2D → Particle

This is the deepest branch of the node tree, and the most algorithmically interesting. CollisionShape2D wraps a Shape2D (circle or rectangle). CollisionObject2D adds the collision-layer/mask machinery and auto-registration with the PhysicsServer. PhysicsBody2D adds mass, velocity, acceleration, and the impulse-based collision solver. Particle is a concrete circle-body that pre-assembles a Sprite2D + CollisionShape2D child pair so you can spawn one with a single constructor call.

CollisionShape2D

: public Node2D classes/node/canvas_item/node2d/collision_shape2d/CollisionShape2D.hpp
CollisionShape2D is a Node2D wrapper around a heap-allocated Shape2D. It is intended to be added as a child of a CollisionObject2D (or subclass). The PhysicsBody2D::collideWith dispatcher uses findClass("CollisionShape2D") on its children to locate the shape — this indirection lets a single body carry multiple shapes (although only the first is currently used) and lets shapes be swapped at runtime without touching the body.

Public API

public CollisionShape2D & setShape(float width, float height) noexcept
Allocate or mutate a RectangleShape2D. If the current shape is a circle, replaces it (frees old shape, allocates new).
public CollisionShape2D & setShape(float radius) noexcept
Allocate or mutate a CircleShape2D. Same replace-if-different-type logic.
public const Shape2D * getShape() const noexcept
Const accessor. Returns nullptr if no shape has been set yet.
public CollisionShape2D & setParentPos(const Vector2 &) / setParentRotation(float) noexcept
Convenience: forward a position/rotation change to the parent Node2D. Useful when you've grabbed a CollisionShape2D* handle and want to move the owning body.
virtual void drawDebug() const noexcept override
Renders the underlying shape with a semi-transparent dark-blue fill and a solid outline. The rectangle variant uses Rectangle::Draw with a center pivot so it rotates correctly with _rot.
Design note. CollisionShape2D deliberately owns its Shape2D via a raw pointer with manual delete in the destructor. Shape2D is a small polymorphic type and using unique_ptr here would add an extra indirection on every collision query, which the engine tries to avoid.

CollisionObject2D

: public Node2D classes/node/canvas_item/node2d/collision_object2d/CollisionObject2D.hpp
CollisionObject2D is the registration boundary for the collision system: its constructor calls PhysicsServer::addCollisionObject(this), its destructor calls remove. It also stores the layer/mask pair (currently informational — the engine does not yet filter collisions by layer/mask in getCollisions, but the fields exist for future use). Area2D (sensor) and PhysicsBody2D (rigid body) both inherit from here.

Public API

public int getCollisionLayer() / setCollisionLayer(int) noexcept
Bitmask describing which layers this object lives on. Default 1 (layer 0).
public int getCollisionMask() / setCollisionMask(int) noexcept
Bitmask describing which layers this object scans against. Default 1.
public bool isEnabled() / setEnabled(bool) noexcept
Master toggle. Disabled objects still exist in the server's map but are excluded from collision queries (reserved for future use; getCollisions currently does not check this flag).

Area2D

: public CollisionObject2D classes/node/canvas_item/node2d/collision_object2d/area2d/Area2D.hpp
Area2D is the "sensor" variant of a collision object: it participates in PhysicsServer::getCollisions queries but does not have mass/velocity and does not push other bodies around. In Godot this is the difference between an Area2D (detect overlap) and a RigidBody2D (resolve contact). The current implementation is a stub — it inherits all behavior from CollisionObject2D and adds nothing yet. The class exists as a hierarchy placeholder so you can findClass("Area2D") to distinguish sensors from bodies.

PhysicsBody2D

: public CollisionObject2D classes/node/canvas_item/node2d/collision_object2d/physics_body2d/PhysicsBody2D.hpp
PhysicsBody2D is the heart of the collision system. It carries linear & angular velocity/acceleration, mass, friction, restitution, static-ness, and rotation-lock. Its constructor also auto-registers with GravityServer::addBody(this), making it the only class that touches all three servers (RenderServer via CanvasItem, PhysicsServer via CollisionObject2D, GravityServer via itself). The resolveContact method is a textbook rigid-body impulse solver with rotational terms.

Physical state

FieldTypePurpose

_angularVelVector2Angular velocity stored as Vector2; only .x is used (rad/sec). .y kept at 0 for type uniformity.
_linearAcc / _angularAccVector2Accumulators. applyForce adds; updatePhysics consumes & resets to zero.
_massfloatDefault 1.0. Used by applyForce as acc += force / mass.
_frictionfloatCoefficient for applyFriction. Default 0.1.

Forces & motion

public PhysicsBody2D & applyForce(const Vector2 &force) noexcept
Adds force / _mass to _linearAcc. Does not immediately change velocity — integration happens in updatePhysics.
public PhysicsBody2D & moveTowards(const Vector2 &target, float strength = 1.0f) noexcept
Steering helper: adds a unit-length force toward target, scaled by strength.
public PhysicsBody2D & moveAwayFrom(const Vector2 &target, float strength = 1.0f) noexcept
Inverse of moveTowards. Useful for flee-style steering.
public PhysicsBody2D & applyGravity(float strength = 9.81f) noexcept
Per-body downward gravity (adds strength to _linearAcc.y). Distinct from GravityServer::applyGravity which does N-body FMM.
public PhysicsBody2D & applyNewtonianGravity(const Vector2 &target, float strength = 9.81f) noexcept
Single-body 1/r² pull toward target. Self-contained alternative to GravityServer for small N.
public PhysicsBody2D & applyFriction(float strength = 0.1f) noexcept
Adds a force opposing _linearVel, magnitude strength * _mass. Becomes a no-op at zero velocity.
virtual void updatePhysics() noexcept override
Per-frame integration: vel += acc * dt; pos += vel * dt; acc = 0. Angular variant only if !_lock_rotation. No-op if _is_static.

Collision resolution

public PhysicsBody2D & collideWith(PhysicsBody2D &other, float restitution = 1.0f) noexcept
Dispatcher. Finds the first CollisionShape2D child of each body, inspects both shapes' getClassName(), and dispatches to one of the four shape-pair variants. Returns *this (fluent).

public PhysicsBody2D & collissionCircleRectangle(PhysicsBody2D &other, float e) noexcept
Clamps the circle center to the rectangle's AABB to find the closest point; that's the contact point. Normal points from contact toward circle center.
public PhysicsBody2D & resolveContact(other, normal, contactPt, overlap, inertiaA, inertiaB, e) noexcept
The shared impulse solver. Steps: (1) positional correction proportional to inverse mass; (2) compute velocity at contact point using v_contact = v_linear + ω × r; (3) compute relative velocity along the normal; (4) if bodies are separating (v_rel · n ≥ 0) return early; (5) apply the impulse magnitude formula below; (6) update linear & angular velocities.
The impulse magnitude is the textbook rigid-body formula including rotational terms: $$ j \;=\; \frac{-(1+e)\,(\mathbf{v}_{\text{rel}} \cdot \hat{\mathbf{n}})}{\tfrac{1}{m_A} + \tfrac{1}{m_B} + \tfrac{(\mathbf{r}_A \times \hat{\mathbf{n}})^2}{I_A} + \tfrac{(\mathbf{r}_B \times \hat{\mathbf{n}})^2}{I_B}} $$ where e is restitution, r_A/r_B are lever arms from each body's center to the contact point, and I_A/I_B are moments of inertia. The impulse vector is J = j · n̂, applied linearly as v += J/m and angularly as ω += (r × J) / I.

Shapes: Shape2D → CircleShape2D / RectangleShape2D

Shapes are detached from the scene graph — they inherit from Object (not Node) and live as heap-allocated members of Sprite2D or CollisionShape2D. They implement two concerns: drawDebug(pos) for visualizing the shape, and collides(thisPos, other, otherPos) for collision detection. The collision system uses a manual double-dispatch via getClassName() string comparison to pick the right pairwise test.

Shape2D

: public Object (abstract) classes/shape2d/Shape2D.hpp

RenderServer is the simplest of the three singletons. It maintains a static map of every CanvasItem in the engine (auto-populated by CanvasItem's constructor) and exposes a single render() method that iterates the map, culls off-screen items, and calls draw() / drawDebug() on each visible one.

Server: PhysicsServer

PhysicsServer is the second singleton. It maintains a uniform spatial hash grid over every CollisionObject2D in the engine and answers "who is near me?" queries in O(1) average time. The cell size is fixed at 10.0 world units — small enough for tight particle clusters, large enough that the 3×3 neighborhood query is cheap.

PhysicsServer

Server: GravityServer — Fast Multipole Method Deep Dive

This is the algorithmic crown jewel of the engine. GravityServer computes pairwise N-body gravitational acceleration for thousands of bodies in real time by implementing the 2D Fast Multipole Method (FMM), reducing the naïve O(n²) all-pairs computation to O(n log n). The implementation is based on Greengard & Rokhlin's classic 1987 paper, specialized to 2D using complex-plane potential theory.

GravityServer

: public Object (singleton) classes/gravity_server/GravityServer.hpp
The naive N-body gravity loop is O(n²) — for 2000 particles that's 4 million pairwise force computations per frame, which is unplayable. GravityServer exists to make N-body gravity feasible at interactive frame rates. The FMM achieves O(n log n) by grouping bodies into an adaptive quadtree, approximating far-away groups via truncated multipole expansions, and only doing exact pairwise computation for nearby bodies. The accuracy/performance trade-off is controlled by a single tunable parameter THETA.

FMM Theory — Why It Works

The 2D gravitational potential of a point mass m at position z_i evaluated at z is:

$$ \Phi(z) \;=\; \sum_i m_i \, \log(z - z_i) $$

Differentiating gives the field (acceleration) at z. The naïve O(n²) loop evaluates this sum directly for every body. The FMM accelerates it by exploiting the fact that when z is far from a cluster of sources {z_i}, the cluster's contribution can be approximated by a truncated Laurent/multipole expansion centered on the cluster's center of mass.

Multipole expansion (P2M)

For a cluster centered at z_0 containing bodies at offsets dz_i = z_i - z_0, the truncated multipole expansion with P terms is:

$$ \omega(z) \;=\; a_0 \log(z - z_0) \;+\; \sum_{k=1}^{P} \frac{a_k}{(z - z_0)^k} $$ $$ a_0 \;=\; \sum_i m_i, \qquad a_k \;=\; -\frac{1}{k} \sum_i m_i \, (z_i - z_0)^k $$

a_0 is the total mass (monopole). a_k for k ≥ 1 are higher-order moments that capture the cluster's internal mass distribution. With P = 6, the expansion is accurate enough that the relative error is below 1% for any z outside the cluster's bounding circle.

M2M — shifting a child's expansion to its parent

When building the quadtree bottom-up, each leaf computes its own multipole expansion from its bodies (P2M). Parent cells then combine their children's expansions via the M2M translation, which re-centers each child's expansion about the parent's center and sums them. The formula involves binomial coefficients:

$$ a_l^{(\text{parent})} \;{+}{=}\; -\frac{a_0^{(\text{child})} \, c^l}{l} \;+\; \sum_{k=1}^{l} \binom{l-1}{k-1} \, a_k^{(\text{child})} \, c^{l-k} $$

where c = z_child - z_parent is the offset between the two centers.

M2L — converting a multipole into a local expansion

During the dual-tree traversal, when two cells are "well-separated" (their bounding circles don't overlap, judged by the θ criterion below), each cell's multipole expansion is converted into a local expansion about the other cell's center. The local expansion is the Taylor-series analog: instead of 1/(z - z_0)^k terms, it uses (z - z_target)^l terms.

$$ b_l^{(\text{target})} \;{+}{=}\; (-1)^l \left[ -\frac{a_0^{(\text{source})}}{l \, d^l} \;+\; \sum_{k=1}^{P} \binom{l+k-1}{l} \frac{a_k^{(\text{source})}}{d^{l+k}} \right] $$

where d = z_target - z_source. The leading (-1)^l comes from the log-derivative symmetry of the 2D kernel.

L2L — shifting a local expansion down to children

Once a parent has accumulated local expansions from all its well-separated source cells, those expansions need to be pushed down to its children. The L2L shift uses another binomial expansion:

$$ c_m^{(\text{child})} \;{+}{=}\; \sum_{l=m}^{P} \binom{l}{m} \, b_l^{(\text{parent})} \, e^{l-m} $$

where e = z_child - z_parent.

L2P — evaluating the local expansion at each body

At a leaf, the final local expansion (combining contributions from all well-separated cells, propagated down via L2L) is differentiated and evaluated at each body's position:

$$ \omega'(z) \;=\; \sum_{l=1}^{P} l \, b_l \, (z - z_{\text{leaf}})^{l-1} $$

The acceleration is then a = strength * (Im(ω'), -Re(ω')) (the sign/real/imag swap comes from the relationship between the complex potential's derivative and the physical gravitational field).

P2P — direct summation for nearby pairs

Bodies in the same or adjacent leaves (not well-separated) are summed directly using the unapproximated kernel m_j / (z_i - z_j). This is the only source of "exact" pairwise computation; for a balanced tree it accounts for the bulk of the work but is bounded by O(n) per leaf × O(n/leaf_count) total = O(n) total.

The θ (theta) acceptance criterion

Two cells A and B are considered "well-separated" (and thus eligible for M2L instead of P2P) if:

$$ \frac{(h_A + h_B) \sqrt{2}}{d(A, B)} \;<\; \theta $$

where h is the cell's half-size. Smaller θ means stricter separation required → more direct P2P work → more accurate. Larger θ means more M2L approximations → faster but less accurate. The engine's default of 0.6 is a common sweet spot from the Barnes-Hut literature.

The per-frame pipeline

Every call to applyGravity(strength) runs the full FMM pipeline:

PassNameDirectionPurpose
1P2MupwardEach leaf builds its multipole expansion from its bodies.
2M2MupwardChild expansions translated & summed into parents (recursive).
3M2LdownwardDuring dual-tree traversal, well-separated cell pairs exchange multipole → local translations.
4L2LdownwardLocal expansions propagated from parents to children.
5P2PdownwardNearby body pairs (in same/adjacent leaves) summed directly.
6L2PdownwardEach leaf evaluates its final local expansion at each body, producing the body's acceleration.

Passes 1–2 happen in rebuild(); passes 3–6 happen in applyGravity(). After L2P, the engine has an unordered_map<ulong, Vector2> of accelerations which it then dispatches back to each body via body->applyForce(accel * body->getMass()).

The adaptive quadtree

Bodies are organized into a quadtree where each node covers a square region of world space. A node either holds bodies directly (leaf) or has four children covering its four quadrants. The tree splits whenever a leaf would hold more than MAX_BODIES_PER_LEAF = 8 bodies, up to a maximum depth of 20. Empty quadrants are skipped (no node allocated), which keeps the tree sparse for clustered distributions.

Why complex numbers? The 2D gravitational kernel log(z - z_i) is naturally expressed in complex arithmetic. The multipole expansion's 1/(z-z_0)^k terms are complex powers; the local expansion's Taylor series is a complex polynomial; the field is the complex derivative. Doing all this with raw (x, y) pairs would require duplicating every operation, so the engine uses std::complex<float> throughout the FMM internals.

Dual-tree traversal

The interact(a, b) function is the core of the M2L step. It takes two quadtree nodes and decides what to do:

  1. If &a == &b (same node): if leaf, do all-pairs P2P within; otherwise recurse into each child with itself, then all child-child pairs.
  2. If wellSeparated(a, b): do M2L in both directions (a's multipole → b's local, and vice versa).
  3. If both are leaves: do all-pairs P2P between their bodies.
  4. Otherwise: subdivide the larger (or non-leaf) side and recurse.

This is more efficient than the simpler Barnes-Hut single-tree traversal because both sides can be aggregates — the asymmetry between "target point" and "source cluster" disappears.

Complexity analysis

ApproachPer-frame cost (n=2000)Notes
Naïve O(n²)~4,000,000 pair testsUnusable for real-time
Barnes-Hut O(n log n)~22,000 operationsSingle-tree, asymmetric

In practice the FMM's constant factor is higher than Barnes-Hut due to the M2L/L2L binomial sums, but its linear scaling wins at large N. For 2000 bodies, the engine sustains 60 FPS on commodity hardware with plenty of headroom for collision & rendering.

main.cpp — Line-by-Line Walkthrough

The engine ships with a single demo application in src/main.cpp. It boots the three servers, spawns 2000 particles in a disc with tangential velocity (so they orbit the center), and runs the standard update loop. This is the canonical usage pattern.

cameraControl — WASD + middle-mouse pan + wheel zoom

The first helper handles camera input. The walk speed is divided by the camera's zoom so panning feels consistent at any zoom level — zoomed in = slower world-space pan, zoomed out = faster. Mouse wheel adjusts zoom with a 10% multiplier per notch, clamped to [0.1, 3.0]. Middle-mouse drag pans by mouse delta (also zoom-adjusted).

C++ 
static void cameraControl(raylib::Camera2D& cam) {
    // Walk speed scales inversely with zoom so panning feels constant
    const float walkSpeed = (1000.0f / cam.GetZoom()) * ::GetFrameTime();
    const float zoomDelta = raylib::Mouse::GetWheelMove() * cam.GetZoom() * 0.1f;
    const Vector2 mousePan = (raylib::Mouse::GetDelta() / cam.GetZoom());

    static const float minZoom = 0.1f, maxZoom = 3.0f;
    Vector2 target = cam.GetTarget();
    if (IsMouseButtonDown(MOUSE_MIDDLE_BUTTON)) target -= mousePan;
    if (IsKeyDown(KEY_W)) target.SetY(target.GetY() - walkSpeed);
    if (IsKeyDown(KEY_S)) target.SetY(target.GetY() + walkSpeed);
    if (IsKeyDown(KEY_A)) target.SetX(target.GetX() - walkSpeed);
    if (IsKeyDown(KEY_D)) target.SetX(target.GetX() + walkSpeed);
    cam.SetTarget(target);
    cam.SetZoom(Clamp(cam.GetZoom() + zoomDelta, minZoom, maxZoom));
}

spawnParticles — disc randomization with orbital velocity

The second helper builds the initial particle distribution. The key trick is that each particle's mass is inversely proportional to its distance from the origin — heavier particles in the center, lighter ones on the periphery. Combined with the tangential velocity (perpendicular to the radial direction), this creates a roughly Keplerian orbital pattern where the central mass dominates and outer particles orbit it.

C++ 
static void spawnParticles(std::vector<Particle*>& bodies, int N,
                                  float spread, float speed = 5.0f,
                                  float minMass = 0.5f, float maxMass = 3.0f) {
    std::mt19937 rng(42);  // fixed seed for reproducibility
    std::uniform_real_distribution<float> distPos(-spread, spread);
    const Vector2 zero(0);
    for (int i = 0; i < N; ++i) {
        const Color col(180+(i%60), 180+((i*7)%60), 220-(i%80), 255);
        const Vector2 pos(distPos(rng), distPos(rng));
        const Vector2 tangent(-pos.y, pos.x);   // 90° rotation = tangent
        const float mass = Remap(pos.Distance(zero), 0, spread, maxMass, minMass);
        Particle* p = new Particle("P" + to_string(i), pos, col);
        p->setMass(mass)
         .setLockRotation(true)                  // particles don't spin
         .setLinearVel(tangent.Normalize() * speed);
        bodies.push_back(p);
    }
}

The main loop — the canonical frame sequence

The main loop is a textbook example of the engine's intended usage. Pay attention to the order of operations: physics rebuild → gravity rebuild → gravity apply → per-body collision queries → per-body physics integration → render. Getting this order wrong is the most common source of "why are my particles jittering" bugs.

C++ 
int main(void) {
    // 1. Boot all three singletons (lazy allocation on first getInstance)
    GravityServer::getInstance();
    PhysicsServer::getInstance();
    RenderServer::getInstance();

    std::vector<Particle*> particles;
    std::vector<CollisionObject2D*> colliders;
    spawnParticles(particles, 2000, 1000.0f);

    raylib::Window window(1600, 900);
    const Vector2 initialPos(window.GetSize() / 2.0f);
    raylib::Camera2D cam(initialPos, initialPos);

    while (!window.ShouldClose()) {
        cameraControl(cam);
        window.BeginDrawing();
        window.ClearBackground();
        cam.BeginMode();

        // 2. Rebuild spatial hash for collisions (every frame!)
        PhysicsServer::getInstance().rebuild();

        // 3. Rebuild FMM quadtree + run upward pass (P2M, M2M)
        GravityServer::getInstance().rebuild();

        // 4. Run downward pass (M2L, L2L, P2P, L2P) + applyForce to each body
        GravityServer::getInstance().applyGravity();

        // 5. Per-body: query nearby bodies, resolve collisions, integrate
        for (Particle* p : particles) {
            colliders.clear();
            PhysicsServer::getInstance().getCollisions(*p, colliders);
            for (CollisionObject2D* pn2 : colliders) {
                if (*p != *pn2) {  // skip self
                    Particle* p2 = dynamic_cast<Particle*>(pn2);
                    p->collideWith(*p2, 0.8f);
                }
            }
            p->updatePhysics();  // vel += acc*dt; pos += vel*dt; acc=0
        }

        // 6. Render visible items (camera-aware culling)
        RenderServer::getInstance().render(window, cam);
        cam.EndMode();
        window.DrawFPS();
        window.EndDrawing();
    }

    // 7. Cleanup: delete particles, then delete all singletons
    for (Node2D* p : particles) delete p;
    RenderServer::deleteInstance();
    PhysicsServer::deleteInstance();
    GravityServer::deleteInstance();
    return 0;
}

Why this order?

StepWhy it must come here
1. Boot serversThe singletons must exist before any new Particle call, otherwise the auto-registration calls in CanvasItem/CollisionObject2D/PhysicsBody2D constructors become no-ops (they all check _instance != nullptr).
2. PhysicsServer.rebuildMust run before any getCollisions call. rebuild re-buckets bodies by their current position — if you skip it, queries use last frame's buckets.
3. GravityServer.rebuildBuilds the quadtree from current body positions. Must come after step 2 conceptually (though they're independent — order doesn't actually matter between 2 and 3).
4. GravityServer.applyGravityComputes accelerations and pushes them into each body's _linearAcc accumulator. Must come before updatePhysics which consumes that accumulator.
5. collideWith + updatePhysicsCollision resolution adjusts velocities; integration consumes accumulated acceleration and updates position. Order within the per-body loop is fine because collideWith only touches velocity, not position.
6. RenderServer.renderLast — draws the post-integration positions. Camera-aware culling skips off-screen bodies for the 2000-particle case where most are out of view.

Set up a 2-body orbit

C++ 
Particle* sun    = new Particle("sun",    Vector2(0,0),    Color::Yellow());
Particle* planet = new Particle("planet", Vector2(200,0), Color::Blue());

sun->setMass(1000.0f);   // heavy central body
planet->setMass(1.0f);

// For circular orbit, v = sqrt(G * M / r). With G=1, M=1000, r=200:
const float orbitalVel = sqrtf(1000.0f / 200.0f);  // ≈ 2.236
planet->setLinearVel(Vector2(0, orbitalVel));  // perpendicular to radius

// FMM will keep them orbiting forever (modulo numerical drift).

Find all children of a class

C++ 
// Find all Sprite2D children of a node:
auto sprites = node->findClass("Sprite2D");

// Find all PhysicsBody2D children:
auto bodies = node->findClass("PhysicsBody2D");

// findClass only searches direct children — for deep searches you need
// to recurse manually:
std::vector<Node*> findAllByClass(Node* root, const std::string& cls) {
    std::vector<Node*> result;
    for (Node* child : root->getChildren()) {
        if (child->getClassName() == cls) result.push_back(child);
        auto sub = findAllByClass(child, cls);
        result.insert(result.end(), sub.begin(), sub.end());
    }
    return result;
}
